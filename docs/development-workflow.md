# Dawn Reader 开发工作方式

_当前阶段：Cloud-first exploration（云端优先探索）_
_确认日期：2026-08-21_

## 判断

现阶段采用云端优先开发是合理的。Dawn Reader 还没有正式用户、付费承诺或需要长期保留的生产数据，快速把改动送到真实托管环境，比反复维护本机环境更有价值。

但这不等于取消验证。新的原则是：**不再把本机运行和本机手工验收作为默认门槛，把主要验证迁到 GitHub Actions 与云端开发站。**

当前 Sites 项目只有一个公开实时地址，没有独立 preview URL。因此从产品阶段看它是开发站，从基础设施角度看它仍是公开部署。任何人都可能访问公开首页，云端数据与访问控制也是真实的。

## 当前默认流程

### 小型、可逆的 Web 改动

1. 从最新 `public/main` 建立短期 `codex/*` 分支，在 checkout 中形成最小补丁。
2. 不默认启动本机开发服务器、浏览器验收或 Simulator。
3. 推送分支并建立 PR，以 GitHub Actions 的测试、构建和安全审计为主要门槛。
4. CI 通过后合并 `main`。
5. 发布合并后的同一个完整 SHA 到当前 Sites 开发站。
6. 只在云端检查本次改动对应的关键路径；失败时优先小步修复或回退到上一版本。

本机 checkout 仍用于编辑、解决冲突和检查 diff。Sites 若要求本机生成部署包，可以运行机械性的构建/打包命令，但不再为同一功能重复做本机手工验收。

### 需要额外审查的改动

所有改动都使用短期分支和 PR；以下类型还必须提供额外审查、迁移或回滚说明，不得只依赖普通 CI：

- D1、R2、IndexedDB 或其他持久化结构与迁移；
- 登录、权限、密钥、隐私边界和公开访问策略；
- 删除、同步、覆盖、批量导入或其他可能丢数据的路径；
- 邮件、通知、支付、发布等外部写入；
- 运行时、框架和关键依赖升级；
- 多个 Agent 或开发者同时修改相同模块；
- 无法通过一次提交安全回退的大型重构。

这类工作使用 `codex/*` 分支并建立 PR，让云端 CI 在合并前运行。涉及数据时还要提供迁移、回滚和旧数据兼容方案。

### iPhone 与 iPad

当前云端流程主要覆盖 Web。GitHub 尚未配置 macOS/Xcode CI，也没有把 TestFlight 设为开发环境，所以原生改动不能用 Web 的云端结果代替。

在配置云端 macOS CI 与 TestFlight 之前，iOS 功能有两个选择：

- 明确暂缓，只交付 Web；
- 把 Xcode 构建、Simulator 或真机验证作为一次显式例外。

任何 Web 云端验收都不能证明 iPhone/iPad 已具有相同能力。

## 什么时候切换工作方式

### 切换到 Beta 工作方式

在出现以下任一信号之前完成切换，而不是出现问题后再补：

- 邀请第一位外部测试者；
- 开始保存无法随时丢弃的真实阅读数据、批注或书籍；
- 两个人或多个 Agent 经常并行开发；
- 开始频繁修改 D1/R2 schema、同步协议或权限；
- 当前公开地址开始被稳定分享和引用。

Beta 阶段需要独立的开发/预览站与 Beta 站、PR 合并门槛、自动迁移测试、数据备份和一键回滚。建议在**邀请第一位外部测试者之前**建立，而不是按日历日期决定。

### 切换到 Production 工作方式

以下任一事件发生时进入生产流程：

- 正式公开发布、收费或承诺稳定可用；
- App Store 或外部 TestFlight 开始分发；
- 真实用户数据不再允许丢失；
- 邮件、通知、支付或其他外部副作用上线；
- 需要支持、监控、隐私承诺或事故响应。

生产阶段必须分离开发、预发布和生产环境；CI 先于合并，迁移可回滚，发布使用精确 SHA，并配置监控、备份、发布后 smoke test 与故障处置。建议在计划公开发布前至少一到两周完成这次切换；如果更早出现不可丢失的数据，则以数据出现时间为准。

## 当前证据口径

- **已推送**：代码进入远端仓库。
- **CI 通过**：云端自动化测试、构建和审计通过。
- **已保存版本**：Sites 接受该 SHA 的部署包。
- **已部署**：该版本成为云端站点当前版本。
- **云端验收**：目标路径在部署地址真实工作。
- **用户验收**：真实使用者确认体验；前述状态都不能替代它。
